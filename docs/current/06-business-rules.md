# Business Rules

This is the current business behavior map for agents. It should be read before changing tests, services, API routes, or UI flows that touch domain behavior.

This file does not replace source code. Treat it as a guide to where rules live and what behavior tests should preserve.

## Rule Ownership

| Rule type | Primary source |
| --- | --- |
| Shared enum values and defaults | `packages/shared/src/constants.ts` |
| Public form/API validation | `packages/shared/src/schemas` |
| Transactional business invariants | `packages/database/src/services` |
| Persistence shape | `packages/database/src/schema` |
| Admin route authorization | `apps/admin/lib/api-auth.ts` and route handlers |
| Browser workflow behavior | `apps/admin/app`, `apps/main/app`, and E2E helpers |

UI should help users avoid invalid actions, but service code should own critical invariants such as stock, payment, status transitions, and accounting math.

## Shared Constants

Current role set:

- `owner`
- `manager`
- `staff`
- `customer`

Only `owner`, `manager`, and `staff` are internal admin roles. `customer` is a storefront/customer identity and should not be treated as admin access.

Important status values:

- Payment: `unpaid`, `partial`, `paid`
- Fulfillment: `pending`, `stock_out`, `completed`, `cancelled`
- Supplier order: `pending`, `ordered`, `received`, `cancelled`
- Purchase order: `draft`, `ordered`, `partial`, `received`, `cancelled`
- Goods receipt: `draft`, `completed`, `cancelled`

Important code prefixes:

- Customer: `KH`
- Supplier: `NCC`
- Order: `ORD`
- Purchase order: `OSN`
- Goods receipt: `PON`
- Supplier payment: `PCH`
- Guest: `guest_`

Runtime defaults:

- Storefront: `http://localhost:3000`
- Admin: `http://localhost:3001` for local work

## Auth And RBAC

Internal admin access is role-based.

- Missing or invalid internal session should return `401`.
- Valid internal user with insufficient permission should return `403`.
- `customer` records do not imply admin access.
- Owner-only behavior should be tested as authorization behavior, not as a generic "security" catch-all.
- Owner-only domains currently include user management and detailed finance/reporting API routes.
- Internal operational routes commonly use "internal" access, which allows owner, manager, and staff.
- Managers and staff role visibility should be treated as route-matrix behavior; audit the route before adding tests because many routes only distinguish internal vs owner.

Internal user behavior:

- User lists exclude `customer` profiles.
- Owners can create internal users with role `owner`, `manager`, or `staff`.
- New internal users get an explicit password or a generated default-length password.
- Reset password applies only to non-customer internal users and generates a temporary password.
- The system must keep at least one owner; demoting, deactivating, or deleting the last owner is rejected by user service code.
- Role/status changes invalidate the profile auth cache for the changed user.

Admin navigation and route visibility:

- The admin sidebar hides `users`, `expenses`, `settings`, `content`, and `widgets` unless the profile role is `owner`.
- The sidebar shows `analytics` to `owner` and `manager`; `reports` is owner-only in the sidebar.
- The sidebar currently shows `homepage` to all internal roles.
- Many settings, homepage, banner, and homepage-collection API routes currently require only an internal session. Do not write owner-only API tests for those routes unless the route matrix is confirmed and implemented.
- Detailed report and finance API routes are generally owner-only; lightweight dashboard analytics APIs allow owner and manager where route handlers explicitly check those roles.

Admin global search:

- The dashboard header has a desktop global search control.
- Search starts only when the trimmed query has at least 2 characters.
- Input is debounced by 300ms.
- Products, orders, and customers are queried in parallel with `limit=4` per domain.
- Results are grouped by domain and support keyboard navigation with arrow keys, Enter, and Escape.

The broad security test suites are intentionally deferred until the app has a route matrix and threat model. Do not recreate tests that assert fake endpoints, generic headers, or tautologies.

## Customers

Customer input validation:

- `fullName` is required.
- `phone` is optional, but if present it must match `0` followed by 9 digits.
- `customerType` is `retail` or `wholesale`.

Customer service behavior:

- Customer phone must be unique among customer profiles.
- Updating a customer may keep the same phone, but cannot reuse another customer's phone.
- Creating a customer record currently does not create a usable auth account.
- Customer code uses the `KH` prefix and is generated by service code.
- Customer deletion is currently a hard delete in the service.
- Customer records have an `isActive` status, and list APIs can filter active or inactive customers.
- Owner and manager can toggle customer active status through the current status route.
- Order creation currently does not reject an inactive customer; do not test inactive-customer order blocking unless product policy and service behavior change.
- Customer stats/spend should be derived from realized, non-cancelled order behavior. Do not count cancelled orders as customer spend.
- Guest customer profiles use deterministic `guest_` codes derived from the guest session ID.

Customer tier behavior:

- The current UI computes customer tier from `orderCount` and `totalSpent`.
- Default thresholds are loyal: at least 10 orders and at least 5,000,000 VND spent; frequent: at least 5 orders and at least 2,000,000 VND spent.
- Current tier logic uses AND for both order count and spend thresholds.
- Loyal tier is evaluated before frequent tier.
- If neither threshold set matches, the UI shows the customer as new.
- Tier thresholds are stored under the `customer_tier_config` setting and edited in the current `/settings` customer tier panel.
- The settings UI validates minimum order thresholds as at least 1 and spend thresholds as at least 0 before saving. The API currently stores numeric values and relies on callers to send sensible values.

Testing implications:

- Important tests should verify create/update persisted state and duplicate-phone rejection.
- Do not test password reset for customers unless real customer auth is reintroduced.
- Do not use legacy OR-based tier expectations unless product policy changes.

## Products And Catalog

Product validation and catalog behavior:

- Product `name` is required.
- Duplicate product names are not currently documented as forbidden; product identity should rely on product ID and variant SKU unless product policy says otherwise.
- `basePrice` cannot be negative.
- Product slugs are generated from normalized product names and made unique with a numeric suffix.
- Public product listing should only return active products.
- Inactive products remain admin-manageable but should be hidden from public storefront catalog/search.
- Category filtering includes descendant categories.
- Product sort/filter behavior is implemented in the product service, not only in UI state.
- "New" product logic is based on products created in the last 30 days.

Category behavior:

- Category `name` is required.
- Category slugs are generated from normalized names and made unique.
- Categories can be hierarchical through `parentId`.
- A category cannot be its own parent.
- Normal category reads return a tree; search returns a flat list of matches.
- Navigation categories are active root categories with `showInNav=true`.
- Category product counts include direct and descendant products where the nav-count service is used.
- Deleting a category currently leaves child categories as roots because the parent FK is `SET NULL`.

Variant and inventory behavior:

- Variant SKUs must be unique within a submitted product payload and against existing variants.
- Product create/edit UI clamps entered `onHand` to non-negative values, but the current DB migration allows `onHand` to go negative after stock-out. `reserved` must remain non-negative.
- New variants start with `reserved = 0`.
- Product deletion is blocked when variants are referenced by order items; use deactivation instead.
- Updating an existing variant cost records cost price history when the cost changes.
- Product images are overwritten by update payloads; first image is treated as primary where applicable.
- Product media UI currently accepts `image/*` files and allows up to 10 images per variant in the product media tab.
- Product image upload API currently only verifies that a file exists and then delegates to storage; there is no documented server-side product image file type or size limit.
- Low-stock status uses variant `lowStockThreshold` when present and the shared default threshold otherwise.
- Inventory movement rows store `onHandBefore` and `onHandAfter`; for a clean chain, each movement's `onHandBefore` should match the previous movement's `onHandAfter` for that variant.
- `productVariants.onHand` should match the latest movement `onHandAfter` after audited stock operations.
- Opening stock is represented as a special `manual_adjustment` movement with note `Opening stock — historical balance` and fixed historical timestamp.
- Updating opening stock requires a non-negative integer, upserts the opening movement, re-chains later movements, and syncs variant `onHand`.

Homepage collection behavior:

- Homepage collections replace legacy hardcoded product sections.
- Active collections render sorted by `sortOrder`.
- Collections resolving zero active products are hidden from the public homepage.
- Supported collection types are `manual`, `best_sellers`, `new_arrivals`, and `by_category`.
- `new_arrivals` uses a default 30-day window when `daysWindow` is absent.
- `by_category` without a category resolves empty and logs a warning.
- Manual collections preserve product ordering through the junction `sortOrder` and filter inactive products.

Storefront banner behavior:

- Banners are managed from the admin homepage surface, not the legacy settings page.
- Banner records are either `custom` or `category`.
- A custom banner requires `imageUrl` at the shared form schema layer.
- A category banner requires `categoryId`; if it has no manual image URL, storefront rendering can derive an image from an active product in that category or its direct children.
- Public storefront banners include only active records whose optional start/end dates include the current time.
- Storefront banners render sorted by `sortOrder`.
- Category banners can derive default title, badge, CTA label, and category URL from the linked category.
- Admin banner reads return all banners without active/date filtering.

Testing implications:

- Product tests should assert persisted product/variant state, not only navigation to a form.
- Cost-change tests should cover history and downstream COGS assumptions when practical.
- Do not test legacy `top/middle/bottom` banner positions as current behavior.

## Orders

Order creation:

- `customerId` can be an existing ID or a customer-like object with phone/name that triggers find-or-create behavior.
- Default delivery preference is `ship_together`.
- `ship_available_first` can split mixed in-stock and pre-order items through split-order logic.
- Order creation locks variants before checking available stock.
- Available stock is `onHand - reserved`.
- Order creation reserves quantity and does not deduct `onHand`.
- Shortage can create supplier orders by default unless `autoCreatePurchaseOrder === false`.
- Initial order fulfillment status is `pending`.
- Initial payment status is `unpaid`.
- Orders require at least one valid item and positive item quantities at the API/form boundary.

Order totals:

- `subtotal` is item unit price times quantity.
- `shippingFee` is non-negative.
- `total` is subtotal plus shipping fee.
- Initial line cost is based on current variant cost, but official COGS is re-snapshotted at stock-out.

Stock-out:

- Stock-out is only valid from `pending`.
- Stock-out locks the order and variants.
- Stock-out decrements both `onHand` and `reserved`.
- Stock-out inserts negative inventory movement with type `stock_out`.
- Stock-out re-snapshots each line's cost from live weighted average cost.
- Order profit after stock-out is based on `subtotal - discount - totalCost`.
- Fulfillment becomes `stock_out`.

Completion:

- Complete is only valid from `stock_out`.
- Complete requires payment status `paid`.
- Fulfillment becomes `completed`.

Cancellation:

- Cancel is only valid from `pending`.
- Cancel releases reserved quantity and does not touch `onHand`.
- Fulfillment becomes `cancelled`.
- Linked supplier orders created for the order are cancelled when identifiable by order note.

Return:

- Return is currently full-order only.
- Return is valid from `stock_out` or `completed`.
- Return increments `onHand` and inserts positive inventory movement with type `cancellation`.
- The order is marked `cancelled`; `stockOutAt` and `completedAt` are cleared.
- Return currently resets `totalCost` to `0`.

Deletion:

- Only cancelled orders can be deleted.

Debt:

- Customer debt queries should focus on stock-out orders that are not fully paid.
- Pending orders are not treated as realized customer debt.
- Debt summary is grouped by customer, sorted by oldest stock-out debt date, and excludes fully paid debt.

History:

- Order lifecycle actions insert status history with both payment and fulfillment status.
- Status history should be used to preserve timelines when current order fields are reset by returns.

Testing implications:

- Important order tests should assert stock reservation, stock-out movement, payment status transitions, and cancellation effects.
- UI-only tests that pass without asserting saved order state are low value.

## Customer Payments

Payment recording behavior:

- Payment amount must be finite and greater than zero.
- Payment method must be one of `cash`, `bank_transfer`, or `card` at the admin API boundary.
- Payments are rejected for cancelled or completed orders.
- Overpayment is rejected.
- New orders start as `unpaid`.
- After recording a positive payment, payment status becomes:
  - `partial` when paid amount is less than order total.
  - `paid` when paid amount reaches order total.
- `paidAt` is set only when the order becomes fully paid.
- Each accepted payment creates a payment row with amount, method, optional reference code, note, creator, and timestamp.
- Order `paidAmount` should equal the sum of accepted payment rows for that order.
- Customer payment API supports idempotency through `clientToken`: the same token and payload should replay the original result, while the same token with a different payload should be rejected by the idempotency layer.

Testing implications:

- Tests should cover partial payment, full payment, overpayment rejection, and complete-order precondition.

## Purchasing, Receipts, And Supplier Payments

Suppliers:

- Supplier code uses the `NCC` prefix and is generated by service code.
- Supplier `name` is required.
- Supplier email, if supplied, must be valid according to the shared schema.
- Suppliers can be active or inactive.
- Default supplier lists hide inactive suppliers.
- Supplier search matches name, code, phone, or email.
- Supplier deletion is currently a soft delete that sets `isActive=false`.
- Supplier stats aggregate legacy supplier orders by status and total actual cost.

Legacy supplier orders:

- Legacy supplier orders are lightweight restocking records tied to a variant and optional supplier.
- New legacy supplier orders start as `pending`.
- Quantity must be a positive integer.
- Transitioning to `ordered` sets `orderedAt` the first time.
- Transitioning to `received` sets `receivedAt` the first time, increments variant `onHand`, and writes a `supplier_receipt` inventory movement.
- `received` and `cancelled` are terminal; changing out of either state is rejected.
- Deleting a legacy supplier order is allowed only when it is `cancelled`.
- Sales-order shortages may auto-create legacy supplier orders by default; this is separate from purchase orders and goods receipts.

Purchase orders:

- Purchase order code uses the `OSN` prefix.
- Purchase orders require at least one item.
- New purchase orders start as `draft`.
- Confirming a purchase order is only valid from `draft`; status becomes `ordered`.
- Cancelling a received purchase order is rejected.
- Receipt application updates item received quantity.
- Purchase order status becomes:
  - `received` when all quantities are received.
  - `partial` when some quantity is received.
  - `ordered` or `draft` when nothing has been received, depending on previous state.

Goods receipts:

- Receipt code uses the `PON` prefix.
- Receipts require at least one item.
- New receipts start as `draft`.
- Receipt payable amount is item total plus extra cost minus discount.
- New receipt paid amount is zero and debt amount equals payable amount.
- Completing a receipt is only valid from `draft`.
- Completing a receipt increments variant `onHand`.
- Completing a receipt inserts inventory movement with type `supplier_receipt`.
- Completing a receipt updates weighted average cost.
- Completing a receipt syncs linked purchase order received quantities.
- Current UI disables receipt completion while supplier debt remains, but the route/service do not enforce that debt check. Confirm the intended policy before adding or rewriting payment-before-receipt tests.
- Cancelling an already-cancelled receipt returns the cancelled row.
- Cancelling a receipt with supplier payments is rejected.
- Cancelling a completed receipt reverses stock and linked purchase order received quantities.

Supplier payments:

- Supplier payment amount must be greater than zero.
- Supplier payment code uses the `PCH` prefix.
- Payment allocated to a receipt must match the receipt supplier when the receipt already has a supplier.
- If a receipt has no supplier, the payment can backfill it.
- Payment amount cannot exceed outstanding receipt debt beyond a small rounding tolerance.
- Deleting supplier payments recomputes receipt payment status and debt.

Testing implications:

- Receipt tests should cover weighted average cost, purchase order sync, and cancellation reversal.
- Do not hard-code payment-before-complete as a service rule until the UI-vs-service policy is confirmed.
- Supplier payment tests should assert receipt debt recomputation.
- Legacy supplier-order tests should not be used as a substitute for purchase order/goods receipt tests.

## Finance And Reports

Official P&L behavior:

- Official revenue is `subtotal - discount`.
- Shipping reimbursement is excluded from official revenue.
- Cancelled orders are excluded.
- Only stock-out or completed orders count for official financial reporting.
- Date filtering is based on stock-out time where the report uses realized order revenue.
- Official COGS uses `order_items.line_cost`, the stock-out snapshot.
- Orders with missing-cost lines are excluded from official P&L until cost data is fixed.
- Missing-cost counts, missing-cost rate, missing-cost order count, and excluded revenue are reported separately.
- Expenses reduce net profit.
- Expenses are classified as `fixed` or `variable`.
- Expense description, positive amount, type, and date are required by shared schema.
- Legacy expense category labels such as rent, salary, ads, shipping, and other are not current shared-schema values.
- Supplier payments are reported as cash movement, not subtracted again from profit because COGS already accounts for product cost.
- Paid but still-pending preorders should not enter official P&L because COGS is not finalized until stock-out.
- Current stock value reports are real-time snapshots: `onHand * WAC/current costPrice`.
- Historical inventory value-over-time is not supported unless a report has a real daily snapshot source.
- Sales by time/customer/order/staff use stock-out time and exclude cancelled orders.
- Sales by time uses order-level `totalCost` and `profit`; sales by product uses line-level `lineTotal`, `lineCost`, and `lineProfit` without allocating order-level discount to product rows.
- Payment reports are cash collection reports, not revenue recognition.
- Purchase reports use completed, non-cancelled goods receipts and date anchor `COALESCE(received_at, created_at)`.
- Purchase payout reports use supplier payment `paidAt`.
- Dashboard and analytics overview metrics are operational summaries and may use paid/completed/order-total formulas; do not copy them as official P&L rules without checking the owning service.

Testing implications:

- Finance math should be covered with service-level tests first.
- Browser report tests should assert filters, export controls, and visible report state, not duplicate all accounting math.

## Storefront

Public storefront behavior:

- Public product APIs should expose active products only.
- Product listing filters and sorting should follow service behavior, not ad hoc client-only filtering.
- Storefront availability should distinguish available, out-of-stock, and preorder states, but exact public labels/timing need product confirmation before strict tests.
- Storefront customer-facing identity is separate from internal admin identity.
- Guest identity uses the `guest_` prefix where guest records are created.

Chat behavior:

- A customer has at most one chat room; room creation reuses an existing room for that customer.
- Chat rooms sort by latest message timestamp.
- Chat room search matches customer name, customer code, or phone.
- Text messages cannot be empty and cannot exceed the shared text length limit.
- Image messages store `[Hình ảnh]` as content and keep the image URL separately.
- Chat image uploads allow JPEG, PNG, and WebP up to 5MB.
- Internal-role messages increment customer unread count; customer messages increment admin unread count.
- Marking messages as read only marks messages from the other party and resets the reader's unread counter.
- Realtime broadcast failure is logged but does not fail a saved message.

Testing implications:

- Storefront E2E tests should create deterministic products and assert visible product details.
- Tests should not pass silently when optional filters or controls are absent.

## Current Policy Gaps To Confirm

These are current implementation behaviors that may need product confirmation before expanding tests around them:

- Customer deletion is a hard delete, not a soft delete.
- Receipt completion payment policy is inconsistent: the UI requires receipt debt to be fully paid before stock is received, but the route/service currently allow completing a draft receipt without that check.
- Order return is full-order only and marks the order as `cancelled`.
- Return resets order `totalCost` to zero after stock is restored.
- Auto-created supplier orders are identified for cancellation through order notes.
- Supplier payment may be unallocated to a receipt; confirm whether this represents supplier advance/credit before testing it as policy.
- Supplier debt aggregate may intentionally count only completed receipts with debt; confirm whether draft receipt debt should be excluded.
- Payment `referenceCode` may need method-specific rules, especially for bank transfer.
- Customer debt aging ranges currently use `minAgeDays`; confirm desired non-overlapping aging buckets before rewriting tests.
- Debt collection FIFO allocation is not documented as current policy.
- Cancelling a completed receipt after later stock-outs needs a clear policy: reject, allow negative stock, or re-chain.
- Partial purchase order cancellation needs policy for received vs unreceived quantities.
- Receipt discount greater than item total plus extra cost needs policy.
- Customer tiers currently use AND-based thresholds and the `Thường xuyên` label; confirm before restoring legacy OR logic or `Mua nhiều`.
- Settings route matrix needs confirmation: owner-only write, manager read, or other split.
- Guest chat phone-based dedupe needs confirmation because current guest profile logic is session-code based.
- AI auto-reply flags and per-room pause behavior need current code verification before documenting as active behavior.
- Session idle timeout and same-browser session replacement need confirmation before becoming auth tests.
- Inactive customers preserving order history but being blocked from new orders needs confirmation.
- Expense categories such as rent/salary/ads/shipping/other are legacy-doc candidates but not current shared schema.

If product policy changes, update this file, the owning service, and the focused tests in the same change. If a rule is missing from this file or looks like old/dead behavior, ask for confirmation before deleting code or rewriting tests around it.
